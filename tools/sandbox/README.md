# Живая проверка в Windows Sandbox

Стенд проверяет Чистовик на настоящей Windows, но **только внутри Windows Sandbox**. Живой ПК он не трогает: вне Sandbox `Sandbox.Live.exe` и скрипты сразу выходят с кодом 3 («Только в Windows Sandbox») и ничего не читают и не пишут.

## Что внутри

| Файл | Где работает | Что делает |
|---|---|---|
| `Run-Sandbox.ps1` | хост | Создаёт `.wsb` (токен запуска, папки, сеть выключена). Сам Sandbox запускает только с `-Launch`. |
| `guest-run.ps1` | Sandbox | Проверяет `WDAGUtilityAccount`, пишет маркер, готовит подписанный тестовый файл, запускает стенд и `installer-check.ps1`. |
| `installer-check.ps1` | Sandbox | Сценарий 8: тихая установка и удаление MSI, ACL каталога, хеш агента, ярлык, запись в «Программы и компоненты». |
| `tests/Sandbox.Live` | Sandbox | Сценарии 1–7 на настоящих портах Native и настоящем `Chistovik.Agent.exe`. В `dotnet test` не входит. |

Защита от запуска не там: стенд требует одновременно учётную запись `WDAGUtilityAccount`, файл `C:\ProgramData\ChistovikSandbox.marker` (его пишет `guest-run.ps1`) и токен в аргументе `--token`, равный содержимому маркера. Токен случайный на каждый запуск и известен только `.wsb`.

## Как запустить

1. Включить компонент «Песочница Windows» (один раз, нужна перезагрузка; делает владелец).
2. Собрать релиз как обычно (`tools\build-release.ps1`, из каталога без кириллицы). Нужны папка publish с `Chistovik.Agent.exe` и (для сценария 8) MSI.
3. Опубликовать стенд (self-contained, в Sandbox нет .NET):

   ```
   dotnet publish tests\Sandbox.Live -c Release -r win-x64 --self-contained -o artifacts\sandbox-stand
   ```
4. Создать конфигурацию (Sandbox ещё не запускается):

   ```
   powershell -File tools\sandbox\Run-Sandbox.ps1 -StandDir artifacts\sandbox-stand -ReleaseDir <publish-x64> -MsiPath <Chistovik-0.1.0-x64.msi>
   ```
   `-SkipIdle` пропускает ожидание простоя агента (~5,5 мин), `-NoProtectedClient` отключает ProtectedClient, если он мешает.
5. Двойной щелчок по созданному `.wsb` (или тот же вызов с `-Launch`). Скрипты внутри запустятся сами.
6. Результаты: `artifacts\sandbox-results\<время>\` — `results.md` и `results.json` (сценарии 1–7), `installer-results.md` и `.json` (сценарий 8), `stand.log`, `guest-run.log`, `DONE.txt` по завершении. Закрытие Sandbox стирает всё, что в нём создано.

## Сценарии

1. **Твики.** Каждый твик каталога в обе стороны отдельной записью: подготовка (значение ставится в противоположное) -> применение через настоящий `OperationHandler` с настоящим журналом SQLite -> независимое чтение реестра -> `Undo` -> проверка возврата. Отдельно: ссылка `HKU\SID\...` -> `HKLM` на месте ключа твика, запись через неё не должна попасть в HKLM.
2. **StartupApproved.** Записи `ChistovikTest_*` в Run (HKU, HKLM 64, HKLM 32) и в папках автозагрузки (пользователя и общей): выключение (12 байт, первый нечётный), откат, включение (первый чётный), откат после включения. RunOnce — ПРОПУСК: 0.1 его не перечисляет.
3. **Питание.** Встроенная схема и откат; параметр `min` (AC) и откат; Ultimate Performance: копия шаблона с заранее заданным GUID (через `IIdGenerator`), активация, откат с удалением только своей схемы. Проверка через `powercfg`. Нет шаблона Ultimate в образе — ПРОПУСК.
4. **Службы.** Тестовая `ChistovikTest_Svc` (sc create, подписанный файл): отключение/ручной запуск и откат, проверка `sc qc`. `Dnscache` и `WinDefend` из запретного списка получают отказ без изменений.
5. **Задачи.** Тестовая `\ChistovikTest_Task` от SYSTEM: выключение разрешено, прямое включение отвергнуто, включение откатом собственного шага разрешено.
6. **Журнал.** (а) читатель без прав администратора (`runas /trustlevel:0x20000`) читает WAL-базу при открытом писателе; (б) дочерний процесс применяет твик и замирает до или после записи реестра (режим в переменной `CHISTOVIK_LIVE_HANG`), его убивают, новый граф агента на том же каталоге восстанавливает pending-шаг (`recovered-done` или `recovered-not-applied`), операция `interrupted`.
7. **Агент и канал.** Настоящий `Chistovik.Agent.exe` (его запускает стенд как администратор): ACL канала, чужой процесс отключается без ответа, Ping, `ApplyTweaks` и `Undo` по каналу, неизвестный тип запроса -> `bad-request`, выход по простою (код 4) либо после ухода клиента (код 0 при `-SkipIdle`).
8. **Установщик** (`installer-check.ps1`): установка, файлы, ACL, хеш агента, ярлык, удаление. Обновление поверх нужно проверять двумя MSI разных версий (не автоматизировано).

Разрушительное делается только над объектами с префиксом `ChistovikTest_` (кроме твиков каталога, которые стенд сам возвращает к исходному значению). Исходная схема питания возвращается.

## UAC и ручной режим

В Sandbox пользователь уже администратор, окно UAC не показывается. Поэтому скрипты не проверяют само окно запроса прав и не запускают GUI: стенд запускает агент как обычный дочерний процесс (режим «агент запущен вручную человеком» без окна). Что остаётся владельцу:

- запуск `C:\Release\Chistovik.App.exe` руками и просмотр экранов (GUI скриптами не вызывается);
- реакция Проводника и «Диспетчера задач» на изменённый флаг StartupApproved: стенд проверяет только байты;
- закрытие App при обновлении и поведение окна UAC на настоящей системе.

## Что не проверено (стенд ни разу не запускался)

Стенд собран и вне Sandbox отказывается работать (код 3), но его прогон внутри Sandbox не выполнялся. Неподтверждённые допущения: пользователь в Sandbox повышен без UAC; `ProtectedClient` не мешает записи в смонтированную папку результатов; `runas /trustlevel` снимает права; WAL читается без права записи; ОС позволяет создать ссылку HKU -> HKLM; самоподписанный сертификат делает файл «подписанным» для WinVerifyTrust. Любое несовпадение даст FAIL или ПРОПУСК с причиной в отчёте, а не ложный PASS.
